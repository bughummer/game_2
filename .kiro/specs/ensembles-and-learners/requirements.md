# Requirements Document

Additional learners (bagging and boosting) and ensemble models (voting and stacking) — new built-in
model plugins, an **open, install-driven catalogue** for any other user-approved learner, and two
ensemble combiners, each saved as its own independently-validatable model version, each trained and
compared through the existing fold machinery, nothing auto-selected.

## Introduction

Training today offers a fixed catalogue: logistic_regression, elastic_net, random_forest, xgboost
and their regressor variants. The owner wants to try more **bagging** and **boosting** learners,
to reach for **any learner on PyPI** (e.g. LightGBM, CatBoost), and to combine trained models into
**ensembles**. This spec adds them under the stock-image decision
(`.kiro/specs/stock-image-migration/decision.md`): the base image is the AWS SageMaker XGBoost
image (which also ships scikit-learn), and per **B10** an experiment may install its own
user-approved `requirements` on top of that image at job start. So the catalogue is **not** closed
to sklearn + XGBoost — it is open to anything a run installs, with no custom image and no ECR push.

Three kinds of thing are added:

1. **Built-in single learners** (ship in the base image, no install needed), as ordinary model
   plugins behind the existing `ModelPlugin` contract:
   - boosting: `HistGradientBoosting` (classifier + regressor), `AdaBoost` (classifier +
     regressor);
   - bagging: `Bagging` (classifier + regressor), `ExtraTrees` (classifier + regressor).
   They register in `ml_engine/models/registry.py` and flow through training, evaluation,
   reporting, importance, grid search and validation with **no orchestration change** — the whole
   point of the plugin contract.

2. **Installed learners** (open catalogue): a learner whose library is not in the base image
   becomes available when the experiment's `requirements` include it (B10). Its plugin may ship
   with the platform (e.g. a CatBoost/LightGBM plugin) and report "unavailable, add to
   requirements" until the package is installed, or be registered on demand. The same
   `is_available()` mechanism the plugins already use reports whether the library is present in the
   current run.

3. **Ensemble combiners** that take several already-chosen base learners and produce one model:
   - **Voting** (phase 1): a fixed combining rule — average predicted probabilities (soft) or
     majority class (hard) for classification, average predictions for regression. Nothing is
     learned on top of the base models, so there is no extra leakage surface and no dependency on
     cross-validation.
   - **Stacking** (phase 2): a learned combiner — a small meta-model trained on the base models'
     **out-of-fold** predictions. It is stronger but it **depends on the cross-validation feature**
     (to produce leak-free out-of-fold predictions) and on the **model-version store** (to hold
     and reference the base models). Stacking is gated on both being present.

All platform invariants hold: SageMaker-only execution; S3-only artifacts; every number from the
deterministic engine; preprocessing and any meta-learning fit on training rows only (per fold);
the LLM may **propose** learners, ensembles and the packages to install but computes no number,
sees no raw data, trains nothing and applies nothing without explicit user approval (LLM boundary
B12); artifacts are versioned Pydantic
contracts whose paths live only in `ml_engine/io/layout.py`; ownership and audit on every mutation;
the default suite runs offline; inherited engine files change only additively with a manifest
update and a written justification.

## Glossary

- **Platform**: ML Factory 2.0 as a whole.
- **Learner**: a single model plugin — one algorithm behind the `ModelPlugin` contract.
- **Base_Learner**: a Learner used as an input to an Ensemble.
- **Ensemble**: a model that combines several Base_Learners into one prediction. Two types:
  **Voting_Ensemble** and **Stacking_Ensemble**.
- **Voting_Ensemble**: an Ensemble with a fixed, non-learned combining rule (soft/hard voting for
  classification, mean for regression). No meta-model.
- **Stacking_Ensemble**: an Ensemble with a learned **Meta_Learner** trained on the Base_Learners'
  out-of-fold predictions.
- **Meta_Learner**: the small second-stage model inside a Stacking_Ensemble (e.g. logistic
  regression / ridge), chosen by the user from the existing Learner catalogue.
- **OOF_Predictions**: out-of-fold predictions — for each row, the Base_Learner prediction produced
  by a fold model that did **not** train on that row. Generated by the cross-validation machinery.
- **Model_Version**: a trained, saved model artifact plus metadata with a stable id (control-UI
  spec). Every Learner fit and every Ensemble fit produces exactly one Model_Version.
- **Base_Image_Libraries**: what the stock AWS XGBoost image ships without any install —
  scikit-learn and XGBoost. Built-in learners use only these.
- **Installed_Library**: a library that is not in the base image and becomes importable only
  because the experiment's `requirements` (B10) installed it (e.g. lightgbm, catboost).

## Requirements

### Requirement 1: Add built-in bagging and boosting learners as plugins

**User Story:** As a data scientist, I want more boosting and bagging algorithms available out of
the box, so that I can compare a wider set with no install step.

#### Acceptance Criteria

1. THE Platform SHALL register the following built-in Learners, each as a `ModelPlugin`, built only
   from Base_Image_Libraries (scikit-learn): `hist_gradient_boosting` (classifier + regressor),
   `adaboost` (classifier + regressor), `bagging` (classifier + regressor), `extra_trees`
   (classifier + regressor).
2. EACH built-in Learner SHALL declare its `supported_problem_types`, availability, default
   parameters, parameter space, native categorical support and feature-importance behaviour through
   the existing `ModelPlugin` interface, so no job, state machine, API or UI code branches on its
   name.
3. THE built-in Learners SHALL flow unchanged through training, per-fold preprocessing, evaluation,
   ranking, reporting, permutation importance, ablation, grid search and validation.
4. THE Platform SHALL expose each built-in Learner's parameter space so grid search (grid-search
   spec) can search it; no new grid-search mechanism is introduced.
5. THE built-in Learners SHALL use only Base_Image_Libraries so they work with no `requirements`
   install; learners needing an Installed_Library are covered by Requirement 2.
6. WHERE a Learner exposes no native feature importance, THE Platform SHALL fall back to the
   permutation-importance path already used for such models, not fabricate importances.

### Requirement 2: Open catalogue — any user-approved learner via the experiment requirements

**User Story:** As a data scientist, I want to reach for a learner that is not in the base image
(e.g. LightGBM, CatBoost), so that I am not limited to sklearn + XGBoost.

#### Acceptance Criteria

1. THE Platform SHALL support Learners backed by an Installed_Library: the learner's `ModelPlugin`
   is importable/usable in a run **when the experiment's `requirements` (B10) installed its
   library**, and reports unavailable (with a "add it to this experiment's requirements" reason)
   when not.
2. THE Platform SHALL use the plugin `is_available()` mechanism already in the contract to gate an
   installed learner, so an absent library degrades to a clear unavailable reason rather than an
   import crash.
3. WHEN a user selects an installed learner, THE Platform SHALL require that the needed package is
   present in the approved `requirements`, refusing submission with the missing package named if it
   is not.
4. AN installed learner SHALL flow through training, evaluation, importance, grid search and
   validation identically to a built-in learner — the plugin contract is the only integration
   point; no orchestration branches on whether a library was preinstalled or installed by B10.
5. THE LLM MAY propose both the learner and the package to add to `requirements`, but the package
   list and its approval are the user's (LLM boundary B12).
6. THE reproducibility guarantee for an installed learner SHALL be the saved per-experiment
   `requirements.txt` (`pip freeze`, B11) recorded on its Model_Version, alongside the image digest.

### Requirement 3: Combine chosen learners by voting (phase 1)

**User Story:** As a data scientist, I want to average several trained models into one, so that I
get a simple ensemble without extra training or leakage risk.

#### Acceptance Criteria

1. THE Platform SHALL let the user define a Voting_Ensemble from two or more Base_Learners drawn
   from the catalogue, with a per-Learner weight defaulting to equal.
2. FOR classification, THE Voting_Ensemble SHALL support soft voting (mean of predicted
   probabilities) and hard voting (majority class); FOR regression it SHALL average predictions.
3. THE Voting_Ensemble SHALL learn nothing beyond fitting its Base_Learners; its combining rule is
   fixed, so it adds no leakage surface and SHALL NOT require cross-validation.
4. THE Voting_Ensemble SHALL be a Model_Version with its own id, recording its Base_Learners,
   their parameters and the voting rule, and SHALL be independently loadable and validatable.
5. THE Voting_Ensemble SHALL fit each Base_Learner on training rows only (per fold under CV_Mode),
   identically to standalone training, so a voting result is comparable to its members.
6. THE evaluation stage SHALL rank a Voting_Ensemble alongside single Learners by the same
   Best_By_CV_Mean rule; THE Platform SHALL NOT auto-select it.

### Requirement 4: Combine chosen learners by stacking (phase 2, gated)

**User Story:** As a data scientist, I want a learned combiner that weights base models by their
out-of-fold skill, so that I can get a stronger ensemble when the data supports it.

#### Acceptance Criteria

1. THE Platform SHALL let the user define a Stacking_Ensemble from two or more Base_Learners and a
   Meta_Learner chosen from the catalogue (default: logistic regression for classification, ridge
   for regression).
2. THE Stacking_Ensemble SHALL train its Meta_Learner on OOF_Predictions produced by the
   cross-validation machinery, so no row's meta-feature comes from a base model that saw that row.
3. IF the cross-validation feature is not present or the experiment is in Single_Split_Mode, THEN
   THE Platform SHALL refuse to build a Stacking_Ensemble and SHALL state that stacking requires
   CV_Mode, rather than silently falling back to in-sample predictions.
4. THE Stacking_Ensemble SHALL be a Model_Version recording its Base_Learners, its Meta_Learner,
   their parameters and the OOF scheme (K), and SHALL be independently loadable and validatable.
5. THE final Base_Learners inside a saved Stacking_Ensemble SHALL be refit on the full training set
   after the OOF meta-features are built, as scikit-learn stacking does, with the Meta_Learner
   fixed from the OOF step.
6. THE Platform SHALL rank a Stacking_Ensemble alongside everything else by Best_By_CV_Mean and
   SHALL NOT auto-select it.
7. THE Platform SHALL compute the fit cost of a Stacking_Ensemble (Base_Learners × (K + 1) for OOF
   and final refit, plus the Meta_Learner fit) into the same Fit_Count_Ceiling / budget guards used
   by grid search and CV, refusing with the numbers if a ceiling is exceeded.

### Requirement 5: User chooses; the LLM proposes and waits for approval

**User Story:** As the owner, I want ensembles proposed and explained but only ever assembled on my
approval, consistent with the platform's LLM boundary (B12).

#### Acceptance Criteria

1. THE LLM MAY propose and describe Learners and ensemble options (including suggesting a
   base-learner set, weights or a Meta_Learner) and MAY explain the voting/stacking trade-off, but
   SHALL NOT apply any of them; what takes effect is the user-approved definition (B12).
2. THE Base_Learner set, the voting rule/weights and the Meta_Learner SHALL be confirmed by the
   user; THE Platform SHALL train an Ensemble only after explicit user approval.
3. THE LLM SHALL NOT select a winning model or ensemble; ranking is presented and the user decides.
4. THE audit trail SHALL record the Ensemble definition (type, base learners, rule or meta-learner,
   K) and who approved it.

### Requirement 6: Save every learner and ensemble as an independent model version

**User Story:** As a user, I want each trained learner and ensemble kept, so that I can validate any
of them later.

#### Acceptance Criteria

1. THE Platform SHALL save each new Learner fit and each Ensemble fit as one Model_Version in the
   model-version store (control-UI spec), with its exact parameters, metrics and training context,
   at a path defined only in `ml_engine/io/layout.py`; no fit SHALL overwrite another's artifacts.
2. EACH Model_Version SHALL be independently loadable and independently validatable on an uploaded
   dataset (control-UI validation flow), including Ensembles (which load their base models).
3. A single Learner or Ensemble failure SHALL be recorded for that model and SHALL NOT abort the
   others (per-model isolation, as today).
4. AN Ensemble Model_Version SHALL reference the Base_Learner Model_Versions it combines so the
   lineage is traceable.

### Requirement 7: Contracts, paths and backward compatibility

**User Story:** As a maintainer, I want learners and ensembles added through versioned, additive
contracts.

#### Acceptance Criteria

1. THE Platform SHALL define the Ensemble definition, the voting rule and the stacking (base set +
   Meta_Learner + K) as versioned Pydantic contracts.
2. THE Platform SHALL add ensemble fields to the training request only as optional fields whose
   absence reproduces today's single-learner training.
3. THE Platform SHALL define every new artifact path only in `ml_engine/io/layout.py`.
4. WHERE an inherited engine file changes (e.g. `ml_engine/models/registry.py` for registration),
   THE change SHALL be additive and recorded in `tests/inherited_manifest.json` with a written
   justification.
5. A built-in Learner or Ensemble SHALL use only Base_Image_Libraries; an installed Learner SHALL
   gate on its Installed_Library via `is_available()` (Requirement 2) rather than importing it
   unconditionally, so the offline suite and a no-`requirements` run never require the package.

### Requirement 8: Offline, deterministic testing

**User Story:** As a developer, I want learners and ensembles covered offline.

#### Acceptance Criteria

1. THE test suite SHALL run with `InMemoryObjectStore`, an in-process orchestrator and mocked AWS,
   with no network.
2. THE suite SHALL include, per new Learner, a test that it registers, reports availability, builds
   with defaults, trains, predicts and produces (native or permutation) importance on a tiny
   fixture.
3. THE suite SHALL include a test that a Voting_Ensemble of two learners fits each member on
   training rows only, combines by the stated rule, and is saved as a distinct loadable
   Model_Version.
4. THE suite SHALL include a test that a Stacking_Ensemble is refused outside CV_Mode, and under
   CV_Mode trains its Meta_Learner on OOF_Predictions whose per-row base prediction never came from
   a fold model that saw that row (the leak-free property).
5. THE suite SHALL include a test that a training request with no ensemble fields behaves exactly
   as today, that built-in plugins import only Base_Image_Libraries, and that an installed-learner
   plugin reports unavailable (not crash) when its Installed_Library is absent in the test env.

## Out of Scope

- A **custom Docker image** or ECR push by us (the open catalogue is reached via the per-experiment
  `requirements` install, B10, not a custom image). Per-framework AWS images are also not used.
- Automated ensemble selection, auto-weighting, or multi-layer stacking beyond one meta-level.
- Blending on a held-out blend set as a separate mode (stacking via CV OOF is the learned combiner
  in scope).
- Auto-selecting or auto-deploying a winning learner or ensemble.

## Dependencies

- **Stacking (Requirement 4) depends on the cross-validation feature** (OOF predictions) and the
  **model-version store** (control-UI spec). Voting (Requirement 3) and the built-in learners
  (Requirement 1) depend on neither and can land first.
- **The open catalogue (Requirement 2) depends on the per-experiment `requirements` install
  (stock-image decision B10/B11/B13).** Built-in learners (Requirement 1) and voting do not.
- All items depend on the **stock-image migration** establishing the base image + install layer;
  this spec is
  written against that boundary and should land after it (or alongside it) so the registry churns
  once.
